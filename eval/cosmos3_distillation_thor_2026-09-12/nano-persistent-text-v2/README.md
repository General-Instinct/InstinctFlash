# Nano persistent cache: slot-owned graph pools

Follow-up to the preserved [v1 stress failure](../nano-persistent-text/stress-receipts/reuse.json). The v1 fallback preserved full action bytes but recorded allocator assertions during graph capture. This experiment assigns a distinct graph pool to each cache slot, so a cleared/evicted slot cannot pass a retired handle into a new capture. Graph statistics retain the history of evicted slots rather than reporting only surviving graphs.

The strict GPU regression now passes, with 144 captures, 180 checks and zero graph rejections across all slot lifetimes. All three 16×32×8 finite action arrays match byte-for-byte, including two evictions and one injected failure followed by a seeded retry. The changed-input check count is 36 beyond the 144 capture checks; the dedicated steady replay counter is zero in this churn-heavy workload. This is not a default runtime change or an acceleration claim. Ten CPU lifecycle/pool-ownership tests pass. The real-model stress run requires no graph rejection, at least 36 captures and 72 checks, plus the existing complete-action, eviction and failed-request retry comparisons. The CUDA memory guard is preserved; a run that never captures enough graphs does not qualify.

`run_stress.py CHECKPOINT OUTPUT --fixture FIXTURE` runs verify/off/reuse serially under the shared Thor lock. The original Nano SDE1 CFG1 checkpoint, cuDNN BF16 attention, plain prompt and 32×8 action contract are unchanged. `pool_lifetime_probe.py` separately compares reuse of a retired pool with fresh handles in tiny isolated CUDA processes; it is a causal diagnostic, not model evidence. The [retired-handle probe](pool-retired.json) reproduces the identical allocator assertion on the second capture while a prior output remains live; the [fresh-handle probe](pool-fresh.json) completes all three cycles exactly. A related upstream allocator assertion is documented in [PyTorch issue 149802](https://github.com/pytorch/pytorch/issues/149802); its multi-device trigger differs, so it does not prove this experiment's root cause.

Launch status is recorded in `launch.json`. The first launch omitted the required fixture argument and terminated at argument parsing; `runner.log` preserves it. The corrected launch uses `runner-with-fixture.log` and the previously absent results directory. Do not restart a live worker or infer success from this source commit. No new student checkpoint has been consumed.

The completed [stress comparison](stress-receipts/comparison.json), source hashes and full action archives were independently verified after transfer. A single `followthrough.py` process admitted a new primary pair only after this strict success. Its latency run completed successfully; results are below. Runs serialize under the existing Thor lock and never retry automatically.


The [six-warmup primary pair](latency-receipts/comparison.json) measured off/reuse p50 **784.771 → 728.270 ms (1.078×)**, p95 **786.369 → 1433.808 ms**. All three full action arrays match finite bytes; 72 captures, 144 checks and 288 steady replays had no rejection. Requests6 and9 still performed expensive graph checks, so this protocol includes preparation costs and does not establish steady-state p95. These measurements are retained unchanged. The additive `nano-cache-steady` study uses12 declared warmups and24 measurements per arm and rejects any capture/check during measured requests. This follow-up does not erase startup or new-prompt preparation costs.
