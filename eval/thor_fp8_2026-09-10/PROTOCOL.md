# Thor native / FP8 Runtime comparison

**pi05 correction:** the current row uses two active cameras (`image`, `image2`) with float32 CHW images in [0,1]. The initial pi05 fixture used an unrecognized wrist key and unscaled uint8 pixels; its result is superseded. See the [audit](ENGINE_AUDIT.md) and [corrected benchmark and receipts](pi05-two-camera/pi05-two-camera-comparison.json). Other rows retain the protocol below.

Each pair uses the same pinned checkpoint revision, recorded camera archive, synthetic state, prompt, denoise schedule and public `Runtime.predict` boundary. Native precision is the default; FP8 is selected explicitly. The 2V/4A VA row is a separate requested operating point, not an FP8 optimization.

All arms run as fresh processes, serially on the same Thor, under the exclusive `/tmp/thor_gpu.lock`. The completed RoboTwin inference service was shut down before the sweep. Frozen 423-file source snapshots and four existing Thor compiled libraries are verified before every arm and after the sweep. Completed arms use source-v1; recovery arms use source-v2 or source-v3, with each receipt identifying its benchmark hash. Only the post-timing E4M3 inventory changes: v2 increases traversal depth, and v3 includes DreamZero’s `eval_utils` wrapper namespace. Inference and timing code are identical. Initial VA attempts failed before loading because an existing local weight download lacked its Hub cache index; all 16 weight files were verified before indexing it. Initial Cosmos FP8 attempts completed inference but failed the shallow inventory check. The pending DreamZero FP8 v1 process was intentionally stopped immediately after launch to use the corrected checker. Failed/cancelled attempts are retained and excluded. Successful native arms are preserved: the validator checks that all source differences are confined to the inventory after timing. DreamZero’s v2 run also completed finite-output timing but failed the wrapper census; its failed receipt is retained, and only that FP8 arm is rerun with v3.

For stateless policies, discard three warmup calls and report median synchronized wall time over 12 generations. pi05 resets its action queue outside every timer: each timed call generates its full 50-action chunk and returns the first decoded action, rather than timing a buffered queue read.

For VA and DreamZero, run four three-cycle episodes. Discard the first episode and measure all nine cycles in the remaining three episodes. These are early-history episode measurements, including each episode's first cycle; they do not measure saturated history. VA receives the same recorded executed-action feedback in both precision arms. DreamZero keeps its native fixed eight-of-sixteen DiT mask and native history.

Loading, reset, observation construction, transport, simulator execution and result serialization are outside the timer. Native image processing, inference and returning CPU actions are inside. CUDA synchronization brackets each timed call. Numeric settings are recorded per arm; native checkpoints and fused engines may configure TF32 differently. Ratios measure the complete selectable Runtime implementations, not the isolated contribution of quantizing a GEMM.

The FP8 arm must produce finite actions and expose actual E4M3 tensors; explicit Cosmos/DreamZero recipes also list their quantized projections. This is not an all-layers-FP8 claim: each family retains its specified higher-precision components. In particular, VLA-4B retains native BF16 vision.

Historical README cells are retained with their original timing boundaries. The new Thor column reports its own matched native → FP8 pair. A ratio below 1 means FP8 is slower. No H100 prototype result supplies a Thor cell.

Latency results do not certify task accuracy or real-time tails. Existing simulator screens retain their own checkpoint, source and protocol scopes. FP8 is lossy arithmetic; its effect on task success must be evaluated separately.
